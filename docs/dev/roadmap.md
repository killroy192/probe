# Roadmap

Principle: **add the terminal path first, delete chat later**, keeping the app runnable after every step.

## Scope decisions

| # | Decision |
| --- | --- |
| 1 | Keep `apps/web` (it is the desktop renderer). Remove hosted/browser runtime mode and `apps/marketing`. |
| 2 | Browser first, then desktop, then mobile (decided 2026-11-02). Desktop work waits until browser functionality is done; track `mobile-impact`. |
| 3 | Remove chat. Features that depend on chat text (linking from text, etc.) are dropped. |
| 4 | A new shell is a plain shell or runs a starting script (a name and a command line, typed once the shell is ready, in the chosen worktree). The user-level script list lives on the default server (the server that serves the UI) and is offered for workspaces on any connected server; a workspace can only disable user scripts or add its own, saved in the workspace file on the workspace's server (PRB.E-002; narrowed 2026-11-08 and 2026-11-09: no env, no folder, no overrides, no separate script tabs for now). |
| 5 | Context from files and the browser flows back into the active terminal. |
| 6 | Agent status comes from a per-CLI adapter, starting with Claude Code: the UI reads the terminal title the CLI sets, and hooks added per session feed the probe CLI that agents read (2026-11-08). Other CLIs run as plain terminals until they get an adapter. |
| 7 | Agents sidebar tree: workspace > project > worktree (labelled with its current branch) > shell, built from live PTY sessions (PRB.E-001). There is no subagent level and no subagent visualization (dropped 2026-11-07, user). No enforcement of how worktrees or agents are created. |
| 8 | The UI is mouse-first: every action works with a mouse or touchpad; hotkeys are optional extras, never the only path (user, 2026-11-02). |
| 9 | Probe's UI is a client of a **remote** server that runs everything: shells, git, worktrees, agents and files. A devcontainer is such a remote, not a special mode: Probe offers a nice way to start a container and connect to it, and nothing else about the container is Probe's business (decided 2026-11-08, user). Isolation, egress rules, credentials and mounts belong to the devcontainer configuration and to the remote server's own environment, not to Probe. |
| 10 | Local UI, remote server (decided 2026-11-08, user): every feature from here on works when the UI runs on one machine and the server on another. No feature may assume the UI can read the server's files, run its commands or reach its loopback; anything the UI needs from the server's machine goes through the server. Phase order: phase 2 (remote server and devcontainer) comes after phase 1 and before agent state. |

## Phases

Reordered 2026-11-01: the hero flow is many agents in one view with live status, so agent state and
the agents sidebar come before review.

0. **Run it**: toolchain installed, app runs in the browser with a working terminal (PRB.T-001).
1. **Terminal-first workspace** (first feature, PRB.E-001): workspaces, a shell tree (project > worktree > shell), standalone shells started in an existing worktree or a new forked one, running a mock agent CLI, with the scenario harness. Next: starting scripts (PRB.E-002); separate script tabs are deferred.
2. **Remote server and devcontainer** (scope decision 9): the terminal-first UI works against a remote server (workspaces, shell tree and "+" all served by that server), then a devcontainer helper starts a container, puts a Linux server in it and connects. First step: a spike that runs the built server in a stock container by hand (`research/devcontainer-attach.md`), which is also how Probe gets developed with Probe.
3. **Agent state and agents sidebar**: Claude Code adapter (terminal title for the UI, per-session hooks for the CLI), status model, notifications, status on the shell tree from PRB.E-001, probe CLI for worktrees and agents.
4. **Review**: CodeMirror pane, comments on any file, batches, MCP tools, expand window.
5. **Context to terminal**: stage a reference into the active PTY without Enter.
6. **Remove chat** in slices: UI, then providers, then orchestration.
7. **Trim**: web mode, marketing, unused providers and source-control packages.
8. **Desktop app**: build, launch and verify Electron, only after the browser functionality is done.
9. **Mobile port** (frozen until desktop settles).
10. **Hygiene**: full local checks baseline and recording it (PRB.T-002), after features land.

Chat is removed late, but agent state must not depend on it: the terminal and hooks are the sources from phase 3.

## Other decisions

Recorded from 2026-11-01; each entry carries its own date where it has one.

- Agent status wiring (2026-11-08, user, after `research/claude-code-hooks-spike.md`; supersedes
  merging hooks into `~/.claude/settings.json`): Probe never edits an agent's global config. The UI
  status comes from the terminal: the shell's foreground process is the agent, and the title it sets
  says working (spinner) or not; this also catches interrupts, which fire no hook, and a running agent
  with no title yet (trust dialog) shows as waiting, with no extra status. Hooks are added per session
  (`--settings`, optionally `--session-id`) through a `claude` shell function in Probe's zsh and bash
  wrappers, so a hand-typed `claude` gets them and nested sessions do not; they feed the probe CLI that
  other agents read. Every status event carries the shell's token. Each CLI gets its own adapter
  (detect, attach hooks, map title and events to Probe's statuses); endpoints are found at call time,
  as `probe kill` does.
- PRB.E-001 decisions (2026-11-02): a workspace is created by Probe and saves its layout; reopening it brings back running shells and lists one that ended unexpectedly for the user to restore, as described in the next entry (supersedes "no persistence" and the earlier "fresh shells on restore" idea); a folder's own checkout is a worktree (shown as its primary worktree); shells are started only from the "+" modal described under "+" and projects below; non-git folders get shells and tabs without git features.
- PRB.E-001 restore (2026-11-02, narrowed 2026-11-07, user, PRB.T-008 planning): running shells survive restarts with scrollback; a shell killed through Probe (tree or in-shell kill command) or exiting normally with any status is removed and never restored. An unexpected end (signal, or the owner process lost) leaves the shell listed as ended, and the user restores it with a Restore action on its row or removes it; nothing restores automatically, there are no attempts or retries, and no agent is resumed (supersedes the 2026-11-02 automatic restore with resume and the "later restores" wording below). A restored shell is a new process in the same place under the same id, with empty output and a "restored" marker. Resuming agents is deferred.
- PRB.E-001 answers (2026-11-02): "Open workspace" is a scrollable dropdown of saved workspaces (one file per workspace in an internal Probe folder, name parsed from the file name, no file picker); switching restores the whole layout and running shells are shown again, removing deletes the file and layout for good, and the app then returns to the start screen. Old chat URLs land on the current workspace, else the start screen. "+" modal choices are remembered per workspace; a failed-start worktree stays pickable; detached HEAD shows the short commit hash. Rename is deferred (out of scope). Scenarios run locally only (no CI) with Playwright as a library. Resolves U-6, U-7, U-8.
- PRB.E-001 "+" and projects (2026-11-05 and 2026-11-06, user, PRB.T-004 review and PRB.T-005 manual pass): a workspace holds **projects**. The sidebar's "Add project" icon opens "Add project to workspace", which only imports an existing folder or creates one with `git init` and starts no shell; importing any worktree of a repository adds the repository. Each project row has a "+" that opens "Create shell": a disabled starting-script dropdown ("mock agent" for now) and, for a git project, an **Existing | Fork** switch with one dropdown. Existing lists every worktree (the primary one first, shown as its branch), and any worktree can hold any number of shells. Fork lists what a new worktree forks from: linked worktrees, a branch named exactly like a linked worktree grouped with it, then the remaining local branches with the primary's current one first; items show the branch on the first line and "<name> worktree" on the second. The modal preselects the project's last start. There is no other start control, and no per-worktree buttons, hiding or worktree management in the tree. The existing add-project flow is not reused (it opens chat drafts); its clone and publish options are deferred to a later story. Shells are named "Shell N · folder · program", N fixed per workspace in start order; rename stays deferred. The 2 s start-to-banner limit is kept (measured 350–380 ms).
- PRB.E-001 branch model (2026-11-05, user, PRB.T-005 planning): the tree shows git's real state, project > worktree > shell, with each worktree node labelled by its current branch ("primary · main" for the repository's own checkout) and shown only while it has running shells; a branch switch in any shell moves all shells of that worktree, and there is no per-shell branch level (supersedes FR-7's "branch a shell was started on"). A shell that changes directory out of its worktree stays under it, marked "elsewhere".
- PRB.E-001 close and kill (2026-11-06, user, PRB.T-006 planning): closing a tab only hides the shell's terminal; the shell keeps running and reopens from the tree. A kill (the tree's "x" after a confirmation, or `probe kill` run inside the shell) force-ends the shell and everything it started, and never deletes a worktree. Removing a workspace kills every running shell in its projects' folders, also when another workspace shares a folder; removing one project from a workspace (a hover action on its row, after a confirmation) does the same for that project and keeps the folder on disk (user, after the PRB.T-006 manual pass).
- PRB.E-001 restart survival (2026-11-06, user, PRB.T-007 planning): one shell host per Probe server (per state folder), a detached helper that owns every shell's terminal wherever the shell's folder or worktree is, keeps shells running while the server is stopped, and lets the next server reattach to the same processes with their output. A workspace file saves its open tabs and selected tab; the shown workspace is remembered per browser. A Probe kill or an exit without a signal (any status) removes the shell for good; a signal exit, or a shell lost with its host, stays listed as ended until removed (the user restores or removes those, PRB.T-008). A project, worktree or shell whose folder is gone is marked "moved"; a shell still running there keeps running, and a project whose folder is gone leaves the workspace once no shell is in it (user, 2026-11-07, PRB.T-007 manual pass).
- PRB.E-002 starting scripts (2026-11-08 and 2026-11-09, user, epic interview): one user level (no profiles); the user list and its Settings page live on the default server, as client-owned settings do; a workspace can only disable a user script or add its own, with no override or rename of a user script, saved in the workspace file on the workspace's server and merged only there; names and commands may repeat, also within one list; concurrent edits merge per script. Plain shell is built in; "mock agent" is the default user script where it can run. A script's program must be found on `PATH` of the workspace's server; env and folder fields are out (the command line can set env). Restore starts a plain shell; running shells are untouched by script edits. Per-project files in the repository (`t3.json`) are later. Each project in a workspace remembers its own last start, worktree choice and script (2026-11-09, user, PRB.T-016 planning; replaces the one remembered start per workspace).
- Remote and devcontainer (2026-11-08, user, after `research/devcontainer-attach.md`): treat a container as a remote server and connect the Probe UI to it, using the existing environment, pairing and route code and its protocol-version check; no extra version policy and no auto-update of the injected server is decided. Probe does not own container safety, backends (Docker Sandboxes and others), or credentials: they come from the devcontainer configuration. Repositories are bind-mounted and worktrees live in a volume, as far as the devcontainer configuration says; Probe supports what it configures. A workspace belongs to the server it is created on (its file lives in that server's state folder). Consequences to carry into the epics: a host `git worktree prune` would drop the metadata of worktrees that exist only in the volume, so they need locking (see `ideas/devcontainer-attachment.md`), and git hooks in a bind-mounted repo run on the host.
- Probe servers and install (2026-11-09, user, PRB.E-003 and PRB.E-004 interviews): "Environments" in Settings becomes **Probe servers**. The UI connects to many servers at once and the workspace list is the union across them; connecting a server, or creating a workspace on one, brings all of that server's existing workspaces into the list. There is no client-side cache: an unreachable server shows as one unavailable entry, and its workspace and shell names are not shown. The default server (the one that serves the UI) holds the client-owned settings (theme, key bindings, general, later commands) and cannot be disconnected or removed; servers own only workspaces, worktrees and shells. A server is connected by direct address and pairing only; SSH forward and the T3 Connect relay are deferred, and the protocol is the same for every connection kind. The render figure is 30 workspaces over 3 servers. The server is built inside the target (container or machine) from the repository with the repo's own toolchain; the install script refuses to run as root, is delivered as a copied file or a one-line `curl`, and takes an explicit port, bind address and state folder. A Linux release package is a deferred story. Users set up the container, the machine and the agent logins themselves; permissions and roles are not part of either epic (every user with access has the same rights). What a published port needs is open until the spike (PRB.E-004 story 1).
- Scenario tests (2026-11-09 and 2026-11-10, user, PRB.E-005, after `research/scenario-harness-analysis.md`): the scenario suite becomes fast and deterministic, in phase 1 beside the terminal-first work. The Playwright library may be replaced by `@playwright/test` (supersedes "Playwright as a library", PRB.E-001 answers); scenarios share a server per worker and run in parallel; setup goes over RPC while one real UI path per action stays; small production signals (prompt ready, layout saved) may be added so scenarios wait on app state, not on guesses; scenarios keep real PTYs, real git, real restarts and pointer-only input, and always run an isolated shell config (a developer's own shell setup is not the suite's concern). Every scenario is saved, atomic and composable, and is either a check or a perf scenario, never both; perf scenarios are `<scenario>.perf.ts` files that run only in a dedicated serial perf run (on request and before a release, and, like the cap gate, only after the user confirms the machine is quiet; perf scenarios are never run by id before it exists). No throwaway driver scripts: the sandbox runs saved scenarios only. Rerunning an unchanged scenario to get a pass, a reading or a diagnosis is forbidden, perf included; a failure must be clear from its first run, and scenarios may add debug-level log lines to product code for that (off at the production default). The KPI is a 20 s cap per atomic check scenario (raised from 15 s, 2026-11-11), checked by a separate gate run once after a scenario is implemented and again only on request, after the user confirms the machine is quiet; full-suite time is not a target. Product performance budgets (such as PRB.E-002's click-to-prompt) belong to product epics, not to PRB.E-005. The rules for writing and running scenarios live in one rules file in `.agents/rules/` (`.claude/rules` links to it), scoped to the e2e files; unit and browser test rules stay in AGENTS.md and `docs/internals/testing.md`. Quick fixes are one story (PRB.T-036).
- UI is mouse-first (2026-11-02, user): epics, stories and scenarios never require keyboard-only paths or hotkeys; shortcuts such as Enter in a modal are optional extras.
- Several agents may share a worktree. Probe creates worktrees and agents through its own CLI; how this is enforced is open.
- First agent integration: Claude Code. Other CLIs run as plain terminals.
- No enforcement of worktree/agent creation. The tree is derived from live sessions tracked through
  server-owned PTYs: a worktree node appears only while a session runs there. An agent that spawns
  another session is shown under its new worktree, or in the same worktree if it stays there.
- Stale status: the server watches the Claude Code process behind each session and clears or marks
  status when it dies, in addition to Paradev-style clearing on terminal exit.

- orchestration-v2 is dropped, not reimplemented. Its docs are deleted in `../probe`; the code is
  removed by the chat-removal epics (phase 6), not in phase 0.
- `probe/docs/terminal-first-app/` was deleted from `../probe` on purpose. The vault is the source
  of truth for new work; `probe/docs/` is written after implementation.
- No CI for now. "Green" means local checks (fmt, lint, typecheck, test). The inherited workflows
  (Blacksmith runners, mobile, relay, release) are left as is.
- An agent may install Node 26.12.1 and pnpm 12.16.1 (PRB.T-001, decided 2026-11-02; this also changes `packageManager` in `../probe/package.json` from the inherited 12.14.0).
