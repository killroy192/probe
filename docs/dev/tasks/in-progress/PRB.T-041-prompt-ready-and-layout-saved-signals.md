# Prompt-ready and layout-saved signals so scenarios stop guessing

## Business Goal

**Problem:** Scenarios guess three facts the app could state. They type into a terminal as soon as a tab is clicked, with no wait for the page's terminal to be attached or for the shell to reach its first prompt, so a line can arrive before the shell reads it. They reload the page or stop the server right after a tab change while the layout save may still be in flight, so the tab strip can come back stale (the suspected S4 flake, epic A-2). They decide that a shell process has ended by polling it for up to 5 s, because the event they could wait on (the shell leaving the list after a kill) is sent before the process has ended. Each guess is a flake source that parallel load makes worse (epic R-4, A-11), and the polling is a temporary lint suppression that names this story.

**Proposed solution:** The app states the three facts and the harness waits on them. The server tells every client when a shell has printed its first prompt; the page shows, per shell tab, whether its terminal is attached and whether the shell is ready, and whether the shown workspace's layout is saved; a shell Probe kills leaves the shell list only once its process has ended. Every wait in the harness that guesses one of these facts uses the signal instead, and the scenario rules say so.

## Expected Behavior

- **Prompt ready (server and contract).** Every shell started in zsh or bash tells every client once that its first prompt has appeared, whether or not a starting script was chosen, through the shell list it already receives: no new stream, no new RPC method and no change to the terminal output protocol. The one existing scan serves both the script typing and the signal; a restored shell and a shell taken over after a server restart are covered too. A shell that never prints the mark (an unwrapped shell, a startup file that replaced the wrapper) is never reported ready, also not after the 15 s script timeout. Where the state lives in the contract and how a takeover knows it are the plan's.
- **Attached and ready (page).** The page shows, per shell tab, hidden tabs included, whether its terminal is attached to the shell and takes input, and whether the shell is ready. The form is the plan's (SU-2); it is part of the page's normal state, not a test-only path, and adds no visible control for users.
- **Layout saved (page).** The page shows whether the shown workspace's layout, as this page last changed it, has been saved: pending while any save of it is in flight, saved once the server has confirmed the last one, failed when the last save failed (today's `layoutError` message stays and clears on the next success). Before this page has changed the shown workspace's layout (after a load, a reload, or showing another workspace), it shows saved, since what it shows is what the server holds. A change made by another client does not make this page pending.
- **Process end (server).** A shell Probe kills leaves the shell list only once its process has ended, so the removal is a fact a client can rely on (SA-4; the user confirms the visible effect, SU-3). "Its process" is the shell process the summary's `pid` names, not its background jobs. A kill does not hang on a shell process that does not end: the server waits for the end no longer than a bound the plan names, at most the terminal manager's kill grace of 1 s (`DEFAULT_PROCESS_KILL_GRACE_MS`, `apps/server/src/terminal/Manager.ts:107`); past it the kill completes and the removal is still sent, and the harness's one pid check then fails naming the shell and pid (ER-3). If the user declines SU-3, the removal keeps today's timing and the plan adds a separate shell-list fact that the shell process has ended, which the harness waits on instead; AC-15 then asserts that fact instead of the removal's order, and AC-16 waits on it. A shell a signal ends keeps today's `ended: "signal"` entry, which already follows the end.
- **The harness waits on the facts.** When this story lands, every wait in the harness that guesses one of the three facts uses the signals, in the library and in the scenarios as they are at that time:
  - typing into a shell waits for its terminal to be attached and the shell ready; a wait that fails names the shell and its last attached and ready states;
  - a reload or server stop that follows a layout change waits for "saved"; a wait that fails names the workspace and its last save state;
  - after ending a shell the server owns, the scenario waits for the shell's end event (the removal, or the `ended: "signal"` entry) and checks the pid once; a pid still alive fails at once, naming the shell and pid;
  - processes the server does not own (S6's background jobs, and S7's shells after their shell host was stopped) have no end event; their check stays a bounded check loop with a permanent class (c) suppression that names the missing event (PRB.T-042 SA-6).
  No lint suppression naming PRB.T-041 remains. A story that lands after this one (PRB.T-038, PRB.T-039) uses the signals for every wait it writes (epic, Stories: whichever of PRB.T-038, PRB.T-039 and PRB.T-041 lands last switches the library's waits and the scenarios; PRB.T-038 Expected Behavior "Signals switch rule" and its AC-23).
- **Readable failures and logging.** A wait on a signal races a deadline from the harness's one place for deadlines and fails naming what it awaited and the last state it saw (epic FR-19). A product log line this story adds is at debug level, which the production default (`T3CODE_LOG_LEVEL` Info, `apps/server/src/cli/config.ts:97`) does not print, and prints no token, pairing URL or cookie.
- **Rules.** `.agents/rules/scenarios.md` says how to wait before typing, before a reload or restart after a layout change, and after ending a shell, and loses its PRB.T-041 interim line, in the same change.

### User Flow

The users are the developer and the agents writing or running scenarios.

1. A scenario starts a shell (over the API, from the "+" modal, or by restoring an ended one); its tab appears.
2. The scenario types into it; the harness first waits until the page shows the tab attached and the shell ready, so the line reaches a shell that reads it.
3. The scenario opens, closes or selects tabs, then reloads the page or restarts the server; the harness first waits until the page shows the layout saved, so the tab strip after the reload is the one the scenario set.
4. The scenario kills a shell, or ends it with a signal from outside; the harness waits for the shell list's end event and checks the pid once.
5. When a wait fails, the first run's output names the shell or workspace, what was awaited and the last state seen.
6. An agent inspecting the page in the sandbox reads the same facts from the page without reading raw frames.

### Edge Cases

- EC-1: A shell started with a starting script: ready when its first prompt is seen; the script is still typed exactly once, after that prompt (PRB.T-011, PRB.T-016 unchanged).
- EC-2: A shell that prints no mark: never ready, also after the script timeout types the script; the page never claims ready on a timeout.
- EC-12: A first prompt mark that arrives after the 15 s timeout (a slow startup file): the scan has stopped, so the shell stays not ready, plain or script shell alike; it is never reported ready on a guess, and the scan's cost stays bounded (the 15 s bound confirmed by the user, 2026-11-10). Scenario shells use the isolated startup files, which print the mark well within the timeout.
- EC-13: A kill that cannot save the shell list keeps the shell as `ended: "signal"`: that entry, like the removal, is listed only once the shell process has ended (same bound as the removal).
- EC-3: A hidden tab: it stays mounted, so it shows attached and ready like the active one.
- EC-4: A ready shell after a page reload, after a server restart that reattaches it, and in a second client: ready once each page has attached. A shell reattached before it printed its first prompt becomes ready at that prompt. The server must be able to tell whether a reattached shell already printed it; if it cannot, that is a defect in the code or in the test, fixed in this story, never worked around with a fallback wait (user, 2026-11-10).
- EC-5: A restored shell (a new process, PRB.T-008): not ready until its own first prompt.
- EC-6: A shell back at a later prompt (after its agent exits): this story signals the first prompt only; whether any scenario needs more is SU-1.
- EC-7: Several layout changes in quick succession: "saved" shows only after the last save is confirmed.
- EC-8: A layout save that fails (for example the workspace file cannot be written): the failure shows, not "saved". A check that needs a file to be unwritable runs through `unlessRoot` (rules file, "Root").
- EC-9: A shell that ends while a scenario waits for it to be attached or ready: the wait fails at once naming the shell and that it ended.
- EC-10: A shell on a second server: that server's shell list carries its own prompt state (R1 reaches the second server over its own API). A page that shows another server's shells as tabs does not exist yet (PRB.E-003); that case is checked there.
- EC-11: The landing order: whichever of PRB.T-038 and PRB.T-039 have landed, the waits in the harness when this story lands are the ones it switches.

### Error Handling

- ER-1: A save fails: today's failure message stays and the saved state does not show; a later successful save clears it and shows saved.
- ER-2: A client and a server of different versions (one sends or expects no prompt state): the client decodes the summary and treats the state as unknown, never ready; nothing else breaks. Local, remote and relay clients behave the same.
- ER-3: A pid still running after its end event: the scenario fails at once naming the shell and pid; it does not wait.
- ER-4: A shell that never becomes ready or a page that never attaches it: the typing wait fails at its deadline naming the shell and its last attached and ready states, and types nothing.
- ER-5: A layout that never reaches "saved" (a save that hangs): the wait fails at its deadline naming the workspace and its last save state; the scenario does not reload.
- ER-6: A killed shell process that does not end within the kill's bound: the kill completes and the shell is removed; a scenario's one pid check then fails naming the shell and pid (ER-3).

## Technical Scope

- **Layers:** server (the shell service's first-prompt state, including restore and takeover, and the order of a kill's removal and the process end), contracts (the shell summary), client-runtime and web (the attach state, the shell's ready state and the layout save state, exposed on the page), scenario harness (the library's typing, reload, restart and process-end waits, the scenarios that call them, self-tests for the negative controls, the suppressions PRB.T-042 left for this story), the scenario rules file, the terminal runtime page.
- **Docs impact:** `.agents/rules/scenarios.md`: "Waiting" says which signal each kind of wait uses and that a check loop remains only for processes the server does not own; the PRB.T-041 interim line goes. `docs/internals/terminal-runtime.md`: the first-prompt scan serves every wrapped shell (restore and takeover included) and publishes the state, and a kill's removal follows the process end; today it says only that `Shells` types after the first mark (`terminal-runtime.md:47-62`). No `docs/user/` change: no visible control changes. AGENTS.md, `docs/internals/testing.md` and `docs/operations/development.md` are not changed.
- **Mobile impact:** the shell summary contract changes, so `apps/mobile` must still type-check; no mobile code is expected to change.
- **Surface checklist (AGENTS.md "Hit every surface").**
  - Entry points: the state belongs to the shell, so it holds for shells started from the tree, the "+" modal, the tab strip, the Workspaces menu and over the API, and for Restore; the `probe` command starts nothing (it only kills, and `probe kill` is a Probe kill).
  - Clients: the browser is the target; desktop wraps it; mobile compiles. Shared state logic goes in `packages/client-runtime` where web and mobile share it.
  - Agent CLIs: the mock agent only: ready is the shell's prompt before the script is typed. Claude Code and every other CLI: plain terminal here, no adapter and no agent status.
  - Shells: zsh and bash (wrapped) report ready; fish and others never do (EC-2); the scan reads output, so Linux and macOS behave alike.
  - Agents: the prompt state is a shell-service fact on the shell list, so `probe` or MCP can reach it later without handler code; no new command now.
  - Contracts: the shell summary; server, web, mobile and desktop follow.
  - Reverse states: ready resets on restore (EC-5) and ends with the shell; saved goes back to pending on the next change; a failure clears on the next success.
  - Lifetimes: after a reload, a server restart and with a second client (AC-4).
  - Connection modes: the same websocket path for local, relay and tunnel; a second server's shell list carries its own prompt state (AC-10), and showing another server's shells as tabs is PRB.E-003's; the UI never reads the server's files or process table.

## Non-functional Requirements and Constraints

- No new stream, no new RPC method, no change to the terminal output protocol or its framing; the scan stops at the first mark or its 15 s timeout (EC-12); no continuous repaint (AGENTS.md "Performance without compromise" and "Taste"; epic R-5). No budget is set or measured here (epic Out).
- One first-prompt scan per shell serves both the script typing and the signal.
- Wire shapes live in `packages/contracts`; the server feature is a service method, not handler code (AGENTS.md "Taste").
- The page states are part of the page's normal state, not a global or code path that production carries only for tests.
- Product log lines added here are at debug level and print no token, pairing URL or cookie (epic FR-20, NFR-3).
- The harness follows `.agents/rules/scenarios.md`: waits subscribe to an event raced against a named deadline; a bounded check loop only where no event exists, with a permanent class (c) suppression naming the missing event; no fixed sleep; pointer-only input; every scripted check is a saved, registered scenario or self-test; a check scenario records no duration; no rerun of an unchanged scenario on unchanged code except the N-run loop of AC-24.
- Scenarios run an isolated zsh or bash (`scripts/scenarios/isolation.ts:20-34`); a developer's own shell config is not the suite's concern.
