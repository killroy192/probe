# Atomic, composable scenarios: one purpose each, checks apart from perf scenarios

## Business Goal

**Problem:** Every scenario today is one linear script. S2, S3 and S7 hold about 20 stages each and E2-S1 ten; even the short ones (S4 to S6, S8) chain several behaviors. An early failure hides every later criterion, a stage often depends on a shell or folder an earlier stage made, and no agent can run "just the restart behavior" or build a bigger flow out of existing checks. The scripts restart the server 14 times, often only to change a startup condition. S2, S3 and E2-S3 both check behavior and record durations. Most scenarios use fixed names and folders, some change state the whole server shares (the starting-script list, the server's state folders), and S6 finds its background jobs with a process-table pattern that any other run would match, so PRB.T-037's sandbox has to refuse them. Nothing measures the 15 s cap yet, and a failure message often names what was expected but not what was found.

**Proposed solution:** Replace every scenario with atomic ones: each proves one behavior, builds its own preconditions through PRB.T-038's library, states what it needs from its server, and is either a check scenario or a perf scenario in a `<scenario>.perf.ts` file. Atomic scenarios can be composed into saved bigger scenarios and grouped into named sets, which the old ids become, and sets and composed scenarios run on the sandbox too. Every failure names what was expected and what was found. A cap gate command times atomic check scenarios against the 15 s cap, and this story runs it once for every scenario it implements. Every acceptance criterion the old scenarios prove is mapped to a new scenario, and nothing on the epic's must-not-change list is given up.

## Expected Behavior

Every old scenario is replaced by atomic scenarios, perf scenarios, sets and composed scenarios built on PRB.T-038's library and PRB.T-037's statement of needs. Nothing is proved less than before.

- **Atomic check scenarios.** Each proves one behavior, which its title names. Several old criteria stay in one atomic scenario only when they are consequences of the same action; the mapping says why. Each builds every precondition it needs through the library, from what it is given and nothing else, so it never reads what another scenario left and runs alone by its id. Each has its own id, made of the old id it came from and a part name, so the old id stays recognisable in the output. The desk analysis's split plans (S2, S3, S7, E2-S1) are a starting point; this story applies the same rule to every scenario.
- **Account of criteria.** Before an old scenario is deleted, every one of its acceptance criteria and stages is listed in this ticket's handoff against the new scenario that proves it, with the new id. That table is also the mapping note the epic promises to tickets that cite old scenario ACs, so their citations stay resolvable.
- **Stated needs.** Every scenario states what it needs from its server, using PRB.T-037's statement: a restart (stopping the shell host counts as one), a pristine home, a second server, a change to server-wide state, or a server started under a condition (an environment variable, a faulty git config). The sandbox refuses every one of these needs, naming it; on the runner each gets a server of its own (PRB.T-040 takes the condition need over with its EC-17 rule). After this story no registered scenario is refused on the sandbox as "not yet safe on a shared server" or for stating no needs. The handoff lists each scenario's needs with the assertion or step that causes each.
- **Server-wide state.** The starting-script list stays server-wide: it is one file per state folder in the product, so E2-S1's and E2-S4's successors that write it, the S2 and S3 successors that add a script to it, and E2-S3's successor that asserts what a fresh state folder offers all state a change to, or a dependence on, server-wide state. So do the successors that make the server's own state folders unwritable (S1 AC-16 and AC-17, S7 AC-18 and AC-21). This answers PRB.T-040's EC-17: these get a fresh server on the runner and are refused on the sandbox. Scenarios that rely on the default list (the "mock agent" entry) run on a shared server because no scenario that shares one writes the list.
- **Restarts.** A scenario restarts the server only when restart behavior is its subject: restart survival, a lost shell host, shells that stay gone across a restart, a restored shell after a lost host, a running standalone shell after a restart, and E2-S1's startup rules (preselection after a restart, an emptied list not seeded again, a damaged list not overwritten, no default when the seed is off, then seeding). A restart that only set a startup condition (S2's faulty git config and the restart that clears it, E2-S3's `PROBE_AGENT_COMMAND`) becomes a server started under that condition. A restart that only made the server see a new starting script (S2 AC-16, S3 AC-22) goes, since the server reads the list on every call. Every remaining restart is listed in the handoff with what it proves.
- **Shared-server safety.** Names and folders come from the library, unique per call. A scenario acts only on what it created or was handed by an earlier step (it never kills every shell on the server, as S2's AC-16 does today). A scenario that does not state a change to server-wide state asserts nothing that leftovers of earlier scenarios on the same server could change: a count of shells or nodes is taken within its own workspace or project, never over the server's whole shell list. A count over the page counts only the scenario's own workspace, because a page shows one workspace at a time, so S3's page-wide `[data-worktree]` count is safe on a sandbox where scenarios run one at a time; PRB.T-040 scopes it for its parallel case. S1's successors keep the pristine-home need where an assertion depends on an empty home (the start screen with no workspace, the exact Workspaces list) and drop it where it does not.
- **What a scenario leaves.** A scenario does not remove what it created when it ends, so the next step of a composed scenario can use it; a shared server or sandbox drops it when it is stopped (PRB.T-040 EC-2, PRB.T-037 EC-6). A change that affects anything beyond the scenario's own workspace and folders while it lasts (a file or folder made unreadable or unwritable) is undone in the step that made it, pass or fail. S7 AC-19's unreadable file is the scenario's own workspace file, so that successor stays workspace-local and restores it in the step; S1's seeded workspace files show in every page's Workspaces menu, so its successors that seed them state a pristine home or a change to server-wide state.
- **Check and perf scenarios.** No check scenario records a duration. The existing timings with a limit in a product ticket become perf scenarios in `.perf.ts` files, each measuring one value and asserting only that limit: S2's tree node after a start (PRB.T-004 AC-3), S2's start to the banner (PRB.E-001 NFR-1, 2 s), S3's branch label after a switch (PRB.T-005 AC-26, limit SU-2) and E2-S3's click to prompt as the server measures it (PRB.E-002 NFR-1). E2-S3's harness-side click to prompt stays a measure PRB.T-028 can read; its limit, and S3's fork start (no limit anywhere), are SU-1. A product limit is used as written; this story sets no budget of its own and changes none. The default suite, every set and the cap gate never run a `.perf.ts` file; perf scenarios run only in PRB.T-040's serial perf run (epic FR-4); until it exists, a `.perf.ts` id given to any command is refused, saying so. Whether this story may run each one once by its id before then is open (SU-6), since that needs an amendment of epic FR-4. The harness refuses a mix: a check scenario that records a duration fails the run, and so does a perf scenario that asserts anything but its budget.
- **Composed scenarios.** A composed scenario is a saved check scenario made of atomic check scenarios as steps, in a stated order. A step uses what an earlier step returned where the composed scenario hands it over (PRB.T-038's results as values) and builds the rest itself, exactly as when it runs alone. A composed scenario needs everything any of its steps needs. It passes when every step passes; when a step fails, the output names the composed scenario, the failing step, its stage, the expected and the found value, the later steps do not run, and the output says which did not. It is not timed against the cap; each of its steps is, as an atomic scenario. At least one composed scenario exists whose steps come from at least two old ids and are all accepted on the sandbox.
- **Named sets.** A set is a saved, named list of check scenarios (atomic or composed). Running a set runs exactly its members, each as it would run alone. Every old id (S1 to S8, T-002, R1, E2-S1, E2-S3, E2-S4, and E2-S2 or E2-S5 if converted under EC-11) is a set of its check successors. A set cannot name a `.perf.ts` scenario, and ids and set names do not collide.
- **On the sandbox.** A set and a composed scenario run against a live sandbox by name, with no cold start, through the same one-line command shape as a single scenario. If any member of a set, or any step of a composed scenario, states a need the sandbox refuses, the whole run is refused before anything runs, naming each refused member or step and its reason; a set never runs part of its members.
- **First-run diagnosis.** Every assertion in an atomic scenario fails naming what it expected and what it found; with the stage and the scenario id from the runner, and the library's artifacts (debug server log of the failing stage, browser console, screenshot, recorded values, what setup created), the cause is readable from the first run. Self-tests fail on purpose in three ways (a wrong UI state, terminal output that never comes, a server that crashes mid-stage) to show it.
- **Cap gate.** One command runs the chosen atomic check scenarios, or the atomic members of a set, serially, once each, and fails any whose time exceeds 15 s, naming the scenario, its time and the cap. The time it judges includes the scenario's own server start only when the scenario needs a fresh server (a restart, a pristine home, a change to server-wide state, a condition); otherwise the server start is left out (epic KPI). It times nothing until it is told that the user has confirmed the machine is quiet; without that it stops and says to ask the user. It refuses perf and composed scenarios named directly, naming why; given a set, it times the set's atomic members and lists its composed members as not timed. A normal run prints times and never compares them to the cap. This story runs the gate once for every atomic check scenario it implements.
- **S4.** The output that arrives during a reload is released by the scenario after the reload has begun, instead of a `sleep 2` typed before it, and is shown exactly once.
- **S6.** The background jobs carry a value unique to the run, and the scenario finds only processes carrying it; a process of the old `sleep 1601` shape, or one carrying another run's value, is not matched.
- **S3.** The shell that leaves its worktree goes to a folder the scenario owns, not `/tmp`.
- **S1's chat addresses.** Each of the 13 addresses is still checked at least once, and both states (a workspace shown, none shown) are still checked by in-app navigation and by a page load, with fewer navigations than today; which addresses are repeated is left to the plan, since they share one redirect.
- **Absence.** An assertion that something is absent is made only after the event that settles it (a row or tab detached, a shell-list change, the tree showing after a reload), never on a single early sample.
- **Signals.** If PRB.T-041 has landed, the atomic scenarios use its signals; if not, they use the library's waits, and whichever of the two lands last switches them (epic switch rule).

### User Flow

1. An agent changes the kill path and runs only the atomic scenarios that prove it, or the set `S6`, with the rules file's one-line commands, in the suite or against a sandbox.
2. One fails. Its `FAIL` line names the scenario, the stage, the expected and the found value; the artifacts hold the debug log of that stage and the browser console. The agent finds the cause from that run, fixes the code, and runs the scenario again (a change, not a rerun).
3. An agent needs a longer flow (start, close a tab, reopen, kill) and saves a composed scenario of the existing atomic ones instead of writing a script; when a step fails, the output names the step.
4. A developer runs `vp run test:scenarios`: every check scenario runs, atomic and composed, and no perf scenario. Asking about restart behavior, they run the set `S7`.
5. After implementing atomic scenarios, the agent asks the user to confirm the machine is quiet, then runs the cap gate over them and records the times.
6. Before a release, the developer runs the perf scenarios with PRB.T-040's serial perf command; this story only writes them.

### Edge Cases

- **EC-1** A stage that used an earlier stage's leftover (S2 AC-7, S7 "AC-17 after restart", E2-S1 AC-5): its atomic successor builds that precondition itself when run alone, and takes it from the earlier step only inside a composed scenario.
- **EC-2** A criterion that only holds over a whole flow (S2 AC-23, no chat route opened at any point): every S2 successor that drives the UI checks it over its own flow.
- **EC-3** A restart scenario that proved survival of many kinds of state at once (S7 AC-6: an agent shell, a plain shell, a shell with a closed tab, a shell whose folder was removed, a second workspace): its successor keeps that variety in one restart, so it proves at least as much. If it cannot fit under the cap, a step run alone would still build all that state, so a composed scenario does not help: the epic owner either raises the cap for every scenario (epic R-8) or agrees to a split that rewrites AC-6 for this case, recorded in the handoff; there are no per-scenario exceptions.
- **EC-4** A behavior proved by a restart with a changed environment (S2's `git init` failure, E2-S3's `PROBE_AGENT_COMMAND`): proved on a server started under that condition, and the handoff lists how.
- **EC-5** The same atomic scenario runs alone and as a step, or twice in one composed scenario: each run creates its own names and folders, and neither reads the other's.
- **EC-6** A composed scenario hands a step something of the wrong kind: rejected before any step runs, naming the step and the input.
- **EC-7** A set on the sandbox includes a member that needs a restart (the set `S7`): the whole set is refused before anything runs, naming that member and the need.
- **EC-8** A `.perf.ts` scenario is named in a set, or given to the cap gate: refused, naming the rule. A `.perf.ts` id given to the default command is refused, saying perf scenarios run only in the serial perf run.
- **EC-9** A perf scenario misses the product limit it asserts: it fails naming the measure, the value and the limit; this story reports it to the ticket that owns the limit and does not change it.
- **EC-10** A scenario's gate time exceeds 15 s: it is split further, or the epic owner raises the cap for every scenario (epic R-8); it is never rerun unchanged to get under.
- **EC-11** E2-S2 or E2-S5 has landed as a long scenario before this story starts: it is converted like the others (FR-11).
- **EC-12** A decoy process of the old shape (`sleep 1601`), or one carrying another run's unique value, runs while S6's successor runs: it is not matched and the scenario passes on its own jobs.
- **EC-13** The release in S4's successor happens before the reload starts: the scenario fails, since the output would have arrived before the reload (the point of the old `sleep`).
- **EC-14** After the split there are many more scenarios than eight: the run's summary still reports correct counts of what ran, passed and failed.
- **EC-15** A sandbox holds leftovers of earlier runs (shells still running, workspaces): an accepted scenario's result does not change; its assertions are on its own state.

### Error Handling

- **ER-1** An atomic scenario fails: the output names the scenario id, the stage, the expected and the found value; the artifacts of PRB.T-036 and PRB.T-038 are saved.
- **ER-2** A precondition cannot be built (a library setup call fails): the scenario fails in its setup stage naming the call and the server's reason, not later with a missing element.
- **ER-3** S4's release never happens: the scenario fails with a named wait for the output, not a silent pass.
- **ER-4** An id or set name matches nothing: the run exits non-zero saying so; a set naming an id that does not exist is an error before anything runs.
- **ER-5** The cap gate is started without the user's confirmation: it times nothing and says to ask the user first.
- **ER-6** A composed scenario's step fails: the remaining steps are skipped and listed as not run; the composed scenario is reported as failed at that step.

- **Agent CLIs:** the mock agent only; Claude Code and other CLIs are not run.
- **Shells:** zsh and bash through the harness's isolated startup files; S4's release and S6's marker must behave the same under both, on Linux and macOS (SA-7).
- **Docs impact:** the e2e rules file `.agents/rules/scenarios.md` only, in the same change: what an atomic scenario is and how its id is formed; the needs it states, including a change to server-wide state and a server started under a condition, and which needs the sandbox refuses; what a scenario leaves and what it must undo; check vs perf and how a perf scenario runs until PRB.T-040; composed scenarios and named sets, and that old ids are set names; one line each to run a set, a composed scenario and the cap gate, in the suite and on the sandbox; the gate's confirmation. The sentence that existing scenarios are converted in PRB.T-039, the S2 example of an old scenario breaking a rule, and the PRB.T-039 line of "Until later stories land" are removed, and the cap gate section's interim instruction is replaced. `docs/internals/testing.md`, `docs/operations/development.md` and AGENTS.md are only checked: each keeps its pointer and contradicts nothing.
- **Mobile impact:** none; no contract change.

## Non-functional Requirements and Constraints

- The repo test rules and the rules file hold: no sleeps, polling loops or wall-clock reads in check scenarios; waits subscribe to an event raced against a named deadline, a bounded check loop only where no event exists; no per-test timeout argument or retry. Lint passes with no `temporary: PRB.T-039` suppression left; `.perf.ts` files may read the clock; check scenario files gain no new clock exemption, and the rules file's permanent classes (runner bookkeeping, deadlines raced against an event, bounded loops where no event exists) stay as they are.
- Pointer-only input; real PTYs, git worktrees, websockets and restarts; the throwaway-home guard and cleanup by captured PID are unchanged (epic NFR-3, must-not-change list).
- No reruns (epic FR-19): each acceptance criterion is checked by one run on unchanged code; where one run can check several criteria, it does (AC-2 and AC-3 are the suite run and the sandbox set run). A failure found on the way is diagnosed from its first run and fixed in the scenario or the code.
- The cap gate runs only after the user confirms the machine is quiet, on the devcontainer, one run per scenario, no median (epic KPI).
- Pointer-only, mock-agent-only and local-only: no scenario reaches a remote server.
- One library: no scenario file defines a helper another scenario could use (FR-21, PRB.T-038).
