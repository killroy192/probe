# Connect Probe to a remote server and open its workspaces

## Goal

A Probe user connects the Probe UI to one or more Probe servers (the default one, which serves the UI, and any remote one, such as a devcontainer or another machine they set up themselves), sees the workspaces of all connected servers in one list, and creates a workspace on the server they choose; everything about the person (theme, key bindings, general settings) follows them to every server, and each server serves only its own workspaces, worktrees and shells.

## Why and why now

- Today the UI only talks to the server that serves it, and the workspace code assumes that server is "the" server. Scope decisions 9 and 10 in `roadmap.md` make the opposite the rule: the UI is a client of a remote server that runs everything (shells, git, worktrees, agents, files), and a devcontainer is just such a remote.
- Phase 2 (remote server and devcontainer) comes before agent state (phase 3). Every feature built on the local-only assumption after this point (agent status, review, context to terminal) costs more to retrofit, so the seam has to be proven now, while the product is still one screen.
- The connection machinery already exists (the Settings section that connects the web app to servers, routes, pairing, a protocol-version check, automatic reconnect), but the terminal-first screens never used it. This epic connects the two; it builds no new connection protocol. The protocol is identical for every connection kind, a devcontainer and a fully remote machine alike.
- The user changed the concept on 2026-11-09 (settled; they will be recorded in `roadmap.md` on approval, and are listed in Users and scenarios): the UI can be connected to several servers at once, the default server (the one that serves the UI) is just one of them, and who owns which setting is split between the client app and the servers. Deciding that split now keeps every later settings page from being built on the wrong side of it. The user also settled that client-owned settings, commands (starting scripts) included, live on the default server, as they do today; PRB.E-002 is being updated to match (see Dependencies and sequencing).
- Sibling epic PRB.E-004 installs Probe on the remote. E-003 and E-004 run in parallel: E-003 verifies against a harness server, E-004 supplies the real remote. E-003 closes after E-004's verification story. E-004's stock-container spike is phase 2's first step.
- If skipped: devcontainer work cannot start, and the author keeps running Probe and the agents on the same machine, with no isolation (the motivating case in `ideas/devcontainer-attachment.md`).

## Users and scenarios

User: the author first, then a small team of peers who run CLI agents inside a devcontainer or on a build machine. Every user sets up the remote server themselves; installing Probe there is PRB.E-004.

Vocabulary and settled decisions (user, 2026-11-09):

- **Probe server.** A Probe server is one running server and the machine it runs on. The **default server** is the server that serves the UI (the local or hosted server, as today); a **remote** server is any other. The default server is just one of the servers, but it is the one that holds the client-owned settings and the only one that cannot be disconnected or removed (it serves the UI; Q-3). The glossary calls a server an "environment"; that internal word in code and the glossary is not renamed by this epic (see Q-4). The user-facing name is **Probe servers**: the Settings section that today reads "Environments" is renamed **Probe servers** in the UI and in the user docs.
- **Who owns what.** Settings about the person belong to the **client app** and follow the user to every server: theme, key bindings and the general settings, and commands (the user-level starting scripts list is one). **Client-owned settings live on the default server, as they do now**, and the UI applies them whichever server's workspace is shown. A **server** is responsible only for **workspaces, worktrees, shells and what runs on its machine**. The first audit of today's Settings pages into the two kinds is a story-1 item (Notes for stories).
- **Several servers at once.** The UI can be connected to several servers at the same time. Each connected server activates its workspaces in the single workspace list: the list is the union over the connected servers and each entry shows which server it belongs to. A workspace belongs to the server it was created on: its file, its projects, its shells and its own starting-script edits (the scripts it disables or adds) live in that server's state and machine.
- **Connecting brings the workspaces.** When the user connects to a server, or creates a workspace on a remote server, that server brings all of its existing workspaces into the list automatically; there is no per-workspace import step.
- **Connect, disconnect, remove.** **Connect** is a saved server plus a working session. **Disconnect** ends the session, keeps the saved server, and removes that server's workspaces from the list (they are not deleted on the server). **Remove** forgets the server and its credential and likewise removes its workspaces from the list. An unreachable server stays as one unavailable server entry with reconnect and remove actions.
- **No copy.** The UI keeps no copy of a server's workspaces or shells, so their names are shown only while that server is connected.
- **Creating.** The user picks which connected server a new workspace is created on (the default server or a remote one). This replaces the earlier "Local | Remote" mode.
- **First connection kind.** Direct address only: an https or http address (a LAN address, a Tailscale/tailnet address, or a container port published on 127.0.0.1; all the same kind) plus the server's one-time pairing token or URL. Plain http is allowed only on a LAN, tailnet or loopback address, never over the public internet. SSH forward and the T3 Connect relay stay deferred; the protocol is identical for all kinds.
- **Where to connect.** Proposed default: connecting a new server is done in Settings > Probe servers, and also offered from the create-workspace flow when the wanted server is not connected yet (Q-1).

Scenarios:

1. **E3-S1, create on a chosen server.** As a user, in "Create workspace" I pick which connected server the workspace is created on: the default server or a remote one. The remote I want is not connected yet, so I connect it (give the direct address of a server I started, a LAN or tailnet address or a published container port on 127.0.0.1, and its pairing token). Before that works I try a wrong token, then an expired one: each is refused with a message that says which, and nothing is saved. Probe connects with a good token and creates the workspace there. I add a project (the folder browser shows that machine's folders, not mine), press "+", start a shell, and its terminal works. The workspace shows which server it belongs to. I create a second workspace on the default server and it appears in the same list.
2. **E3-S2, many servers, one list, one me.** As a user, I connect a server that already has two workspaces. Both appear in my workspace list at once, labelled with that server, next to those of the default server, with no import step. I reload the UI: they are still there. I open one of each server and my layout and running shells are back (restore works as in PRB.E-001, served by the workspace's own server); each shows only its own server's data. I change the theme and a key binding while one server's workspace is shown, then open the other server's workspace: the theme and the binding are the same, because they live on the default server. A remote workspace's start menu offers my starting scripts list from the default server plus that workspace's own scripts. Settings pages that belong to a server are shown under the server they edit and name it.
3. **E3-S3, a server goes away and comes back.** As a user, I am in a remote workspace. The remote server stops (or the network drops). The shell tree shows a clear "disconnected" state naming the server, the "+" modal cannot start a shell and says why, the server's own Settings pages say they cannot load, and I can still switch to a workspace of another server. In the workspace list that server's workspaces are replaced by one unavailable server entry with a reconnect and a remove action; its workspace and shell names are not shown, because nothing is cached. My theme, key bindings and general settings are unaffected. While the server is down I reload the UI: the start screen offers the other servers' workspaces and shows this server as unavailable, with the reason. When the server returns, the connection comes back on its own, its workspaces return to the list, the tree shows the server's current shells (those that survived as running), and I did not reload.
4. **E3-S4, disconnect and remove.** As a user, I first remove a workspace of the remote server while it is up (its shells are killed and its file is deleted on that server); later, with the server stopped, removing a workspace is refused with a reason. I disconnect a server in Settings > Probe servers: its workspaces leave the list, it stays as one unavailable server entry (no workspace names), and nothing runs on my side. I connect again without pairing again and its workspaces return. I remove the server; a confirmation names what stays on the server, and I accept. Its credential is forgotten, its entry leaves my list, and nothing is deleted on the server. Connecting to it again needs a new pairing.
5. **E3-S5, wrong server version.** As a user, I connect to a server whose protocol version differs from the UI's. Probe refuses to open its workspaces and says which side to update, with no half-working screen, and none of its workspaces enter my list.

Each scenario can pass completely only once its last story is done: E3-S5 in story 3, E3-S1 in story 4 (its pairing refusals from story 3), E3-S2 in story 5 (its workspaces part from story 2), E3-S3 in story 6, E3-S4 in story 7.

Features built so far keep working against a remote: starting scripts (the list is mine and lives on the default server; the command runs on the remote machine), restore, kill and the worktree choices all run on the remote machine (see FR-14).

## Scope

**In:**

- Renaming the user-facing Settings section "Environments" to "Probe servers" in the UI and the user docs (web and desktop).
- The split of settings between the client app (held by the default server) and the servers: the definition, the audit of today's Settings pages, and the pages shown under the right owner.
- The UI connected to several servers at once, with one workspace list that is the union over the connected servers, each entry labelled with its server.
- Choosing the server a workspace is created on, from the default server and the connected remotes.
- Connecting the UI to a remote server by direct address only (https, or http on a LAN, tailnet or loopback address), with pairing and the existing protocol-version check; all of a connected server's existing workspaces enter the list automatically.
- All workspace screens (shell tree, "+" modal, terminals, Add project, server-owned Settings pages that exist today) served by the server the workspace belongs to.
- The reverse states: disconnect, reconnect, remove, and what each screen shows while a server is unreachable.
- A second-server mode in the scenario harness so all of the above is tested without containers.
- The user docs section for connecting to a Probe server.

**Out (non-goals, with a reason):**

- Starting or managing containers: the user starts the remote themselves (user decision 2026-11-09); a "nice way to start a container" is a later story after PRB.E-004.
- Installing or updating Probe on the remote, and any install script: PRB.E-004.
- Agent login, credentials and setup on the remote: belong to the remote's own environment (scope decision 9).
- Several servers inside one workspace (a workspace belongs to one server): user decision 2026-11-09; a later epic if ever.
- Moving or copying a workspace between servers: follows from the same rule.
- Moving client-owned settings off the default server (per-device storage, syncing between devices or browsers): not decided here; they stay on the default server as today, and this epic only makes them independent of which remote server is connected.
- Renaming the word "environment" in code, contracts and the glossary: only the user-facing name changes (Q-4).
- A new version policy: the existing integer protocol check is the only compatibility rule (roadmap, "Remote and devcontainer").
- Isolation, egress rules, mounts and container safety: scope decision 9.
- Desktop and mobile UI: browser first (scope decision 2). `mobile-impact`: mobile has its own server list and keeps its labels; contracts may change, so mobile must still compile, and no mobile UI is built.
- SSH forward as a connection kind: desktop-only, and it installs from upstream releases this fork does not publish. Deferred: a later candidate story or follow-up epic that reuses the same protocol (FR-15).
- The T3 Connect relay as a connection kind: it needs a hosted relay nobody runs for Probe. Deferred: a later candidate story or follow-up epic that reuses the same protocol (FR-15).
- Worktree locking against a host `git worktree prune`: not here, see PRB.E-004 Q-3.
- Plain http over the public internet: refused (NFR-3).
- Chat removal and peer links between servers: not touched.

## Approach

1. Prove the seam first: run the UI against a second server that shares nothing with it and list every place a screen assumes the UI's own server (files, loopback, one environment). At the same time sort today's Settings pages into client-owned and server-owned. The scenario harness learns to start that second server, pre-register it and seed workspaces on it, a test-only seam until the connect flow exists (story 3).
2. Make the workspace list the union over the connected servers and the workspace screens take their server from the workspace, so a workspace opened from a server is served only by it.
3. Add the "Probe servers" Settings section (the renamed section) with the connect flow: direct address only (https, or http on a LAN, tailnet or loopback address), pairing and the version check; connecting brings all the server's workspaces into the list. SSH forward and the T3 Connect relay are deferred and will reuse the same protocol.
4. Add the choice of server to workspace creation.
5. Make the Settings pages follow the split: client pages are held by the default server and are the same wherever a workspace is shown, server pages sit under the server they edit.
6. Add the reverse states and the unreachable displays: reconnect, disconnect, remove.
7. Replay everything built so far (E-001 and E-002 scenarios) against the second server and fix what breaks.

Alternatives considered: copying workspaces to the UI machine and syncing (rejected by the user: a workspace belongs to its server, scope decision 10); a separate "devcontainer mode" with its own protocol (rejected: one identical protocol for every remote); a "Local | Remote" mode switch in workspace creation (rejected 2026-11-09, user: the UI is connected to several servers at once, the default server is just one of them, and the user picks a server); importing a remote's workspaces one by one (rejected 2026-11-09, user: connecting activates all of them); keeping settings about the person on each server (rejected 2026-11-09, user: they belong to the client and follow the user).
